# Session Handoff — AI-Assisted CAD Service

Full project: JSON-IR CAD feature trees, compiled to real geometry via
build123d, generated by a fine-tuned Gemma 4, served through a multi-
service app with a three.js frontend. This file plus the project zip is
everything needed to continue in a fresh conversation.

## What's built (component map)

**Dataset/compiler core** (`cad_dataset/` root):
- `schema.py` / `compiler.py` — canonical JSON IR spec + direct interpreter (no codegen step) into build123d
- `executor.py` — subprocess isolation; `execute_ir()` one-shot, `BatchExecutor` persistent-worker pool (avoids per-call OCP import cost)
- `validator.py` — geometric sanity checks (manifold, volume>0, etc.)
- `gen_single_feature.py` / `gen_chains.py` / `gen_repair.py` / `gen_regenerate.py` — synthetic data generators for the 4 task types
- `build_dataset.py` — orchestrates generation → verify → dedupe (`structure_hash`) → split → chat-format (`to_chat_format`, `prompt`/`completion` shape); `--include-flywheel-data` flag merges verified flywheel records in
- `chat_format.py` — shared turn-rendering (`render_generate_user_turn` etc.), used by both `build_dataset.py` (training) and `llm-service/orchestrator.py` (inference) so wording can't drift between train/serve
- `primitives.py` — parameter samplers, safe ranges
- `stub_build123d/` — fake build123d for plumbing tests when a real install isn't available

**training/** — QLoRA fine-tuning (transformers/trl/peft), Docker + compose (`train`/`merge` services). `GeometryEvalCallback` reuses `schema.py`/`executor.py` for real geometry-validity eval during training. Explicit VRAM+RAM unload around eval's `generate()` calls (allocator fragmentation from interleaving backprop and KV-cache growth). `RESUME_FROM_CHECKPOINT` support.

**service/** — geometry microservice (FastAPI). `POST /v1/compile` (validate only), `POST /v1/export` (STEP/STL/GLB). `schema.validate_bounds()` rejects absurd IR (huge pattern counts, huge dimensions) before touching a worker — both here and inside `compiler.py` itself as the actual last line of defense.

**llm-service/** — inference orchestrator + product backend.
- `orchestrator.py` — self-correcting generate/repair loop against llama.cpp + geometry service; `generate_stream()` is the core implementation, `generate()` wraps it for non-streaming callers
- `store.py` — SQLite: projects+versions (undo/redo), request log (`log_event`/`compute_outcomes`, scoped by `user_id` — auth step 7), users/sessions, `verify_session()`'s lazy session-expiry (auth step 9), legacy-data backfill helpers (`count_legacy_rows`/`backfill_legacy_ownership`, auth step 8)
- `migrate_legacy_owner.py` — one-time CLI backfill driving `backfill_legacy_ownership`; dry-run by default, idempotent (auth step 8)
- `main.py` — FastAPI: `/v1/auth/{signup,login,logout}`, `/v1/generate(/stream)`, `/v1/projects/*` (CRUD, generate, apply, undo, redo, render, log-download — all behind `Depends(get_current_user)`), `/v1/logs*` (scoped by `user_id`)
- docker-compose: `llamacpp` (ghcr.io/ggml-org/llama.cpp) + this service + `convert` profile (HF→GGUF); `SESSION_LIFETIME_HOURS`/`RATE_LIMIT_PER_MINUTE` env passthrough (auth step 9)

**frontend/** — three-panel React app (feature tree / three.js viewport / chat), titlebar project switcher. Design: charcoal + steel-cyan accent, IBM Plex Mono for technical data, drafting-table register (see `frontend/README.md` for full rationale). Structured editing (click a feature, edit a field, bypasses the model). Download toolbar (STEP/STL/GLB) in the viewport.
- `components/LoginPage.jsx` / `components/SignupPage.jsx` — new (auth step 10)
- `App.jsx` — gates rendering behind `authToken` state; `applyAuth()`/`clearSessionState()` keep React state, `api.js`'s in-memory token, and `localStorage["cad_auth"]` in sync; restores a persisted session on mount before the project-list effect fires (auth steps 10–11); registers a global 401 handler that drops back to login with a "session expired" notice (auth step 12)
- `api.js` — `login()`/`signup()`/`logout()`; every `/v1/projects*` call goes through `authFetch()`, which attaches `Authorization: Bearer <token>` and routes any `401` through a registered handler (auth steps 11–12)
- `components/ProjectBar.jsx` — shows the logged-in email + a Log out button

**Root `docker-compose.yml`** — runs the whole app (`geometry`+`llamacpp`+`llm-service`+`frontend`) as one stack, one `.env`. Deliberately excludes `training/` and `convert` (offline steps).

**`verify_auth_e2e.py`** (repo root) — auth plan step 14: HTTP-driven end-to-end check against a running stack (signup→login→create project; a second user gets 404 on GET/DELETE of the first user's project and it's absent from their list; request-log scoping). Exit 0/1, same convention as `mine_flywheel_gate.py`. Migration (step 8) verification is a flagged **manual** step (`--expect-migrated` prints the `migrate_legacy_owner.py` dry-run command) — no HTTP endpoint exposes legacy row counts by design. **Not run against a live stack in this sandbox** (no network/Docker here) — run it before treating step 14 as confirmed.

**Flywheel pipeline** (`mine_flywheel_*.py`, root) — Phase 4, steps 1-5, 7-9 done, step 6 (PII scrub) and steps 10-11 (scheduling, retraining trigger) are TODO:
1. `mine_flywheel_data.py` — log extraction, outcome/date filtering
2. `mine_flywheel_repairs.py` — walks retry chains to eventual fix
3. `mine_flywheel_edits.py` — pairs "edited" events, synthesizes instruction via IR diff
4. `mine_flywheel_verify.py` — re-verifies via `BatchExecutor`, quarantines drift
5. `mine_flywheel_dedup.py` — dedupes against corpus via `build_dataset.structure_hash`
7. `mine_flywheel_chatformat.py` — converts via `build_dataset.to_chat_format`
8. `build_dataset.py --include-flywheel-data` — merge point, re-checks `verified:true` itself
9. `mine_flywheel_gate.py` — count thresholds, exit 0/1

**⚠ New gap introduced by auth step 7**: `mine_flywheel_data.py` and `mine_flywheel_pairs.py` call `GET /v1/logs`/`GET /v1/logs/outcomes` via bare `urllib.request` with no `Authorization` header. Those endpoints are now behind `Depends(get_current_user)`, so both scripts will 401 against an authenticated stack. No service-account/admin-role concept exists to fix this yet — needs either a dedicated admin bearer token minted out-of-band, or the scripts updated to accept `--auth-token`. Don't run the flywheel pipeline against a real deployment until this is resolved.

## Auth (13 of 14 steps — only step 13 remains)

Full plan, all 14 steps, current status:

1. **Schema** — `users` table (id, email, password_hash, created_at), nullable `owner_id` on `projects`, migration guard (`ALTER TABLE` for pre-existing DB files). ✅ done
2. **Password handling** — `hash_password`/`verify_password`, stdlib PBKDF2-HMAC-SHA256, no bcrypt/argon2 dependency. ✅ done
3. **Token issuance** — opaque session tokens over JWT (need DB-backed revocation anyway). `sessions` table + `create_session`/`verify_session`/`delete_session`. ✅ done
4. **Signup/login endpoints** — `store.create_user`/`authenticate`; `POST /v1/auth/signup`, `POST /v1/auth/login` in `main.py`, both return `{token, user}`. ✅ done
5. **Auth dependency** — `get_current_user` (FastAPI `Depends`): reads `Authorization: Bearer <token>`, `verify_session` → `store.get_user`, 401 on either failure. `POST /v1/auth/logout` behind the same dependency. ✅ done
6. **Scope project endpoints** — `Depends(get_current_user)` on all 10 `/v1/projects*` routes. `_require_owned_project(project_id, user)`: 404 (not 403) on missing-or-not-owned. `create_project`/`list_projects` scoped by `owner_id`. Legacy rows (`owner_id=NULL`) stay accessible to any authenticated user until step 8's backfill runs. ✅ done
7. **Scope the request log** — `user_id` column on `request_log` (+ migration guard), threaded through every `log_event` call; `list_events`/`log_summary`/`compute_outcomes` scoped by `user_id`, with legacy `user_id IS NULL` rows staying visible (same stopgap as step 6). `/v1/logs*` gated behind `Depends(get_current_user)`. ✅ done — **but see the flywheel-scripts gap noted above**, not yet resolved.
8. **Migration for existing data** — `store.count_legacy_rows()`/`backfill_legacy_ownership()`; `migrate_legacy_owner.py` CLI (dry-run by default, `--apply` to write, idempotent — only NULL columns ever touched). Stateless `/v1/generate` events (no `project_id`) are intentionally left unmigrated forever, not a bug. ✅ done
9. **Secrets/config** — no signing secret needed for opaque tokens. `SESSION_LIFETIME_HOURS` wired into `ProjectStore.verify_session()`'s lazy expiry-and-delete-on-read (blank/unset = never expires; revocation via logout is immediate regardless). `RATE_LIMIT_PER_MINUTE` added to `.env.example`/compose files as a config knob only — the knob exists ahead of the middleware that will read it (step 13). ✅ done
10. **Frontend: login/signup UI** — `LoginPage.jsx`/`SignupPage.jsx`; `App.jsx` gates all rendering behind `authToken` state (`authView` toggles between the two). ✅ done
11. **Frontend: token storage** — `api.js`'s `setAuthToken()`/`authHeaders()` attach `Authorization: Bearer <token>` to every `/v1/projects*` call and `logout()`. `App.jsx`'s `applyAuth()` persists `{token, user}` as one JSON blob in `localStorage["cad_auth"]` and restores it on mount, before the project-list effect can fire. ✅ done
12. **Frontend: 401 handling** — `api.js`'s `authFetch()` is the single choke point that detects a 401 and invokes a handler `App.jsx` registers via `setUnauthorizedHandler()`. `clearSessionState()` (shared by explicit logout and the forced case) clears token, user, stored project id, and all in-memory project state together. A forced logout sets `sessionExpired`, shown as a notice on `LoginPage`. ✅ done
13. **Rate limiting (keyed on user_id)** — per-user request budget middleware in `llm-service`. ⬜ **not started.** `RATE_LIMIT_PER_MINUTE` exists as inert config (step 9); nothing reads it yet.
14. **Verification** — `verify_auth_e2e.py` (repo root): signup → login → create project → confirm a second user gets 404 on the first user's project and it's absent from their list → confirm request-log scoping (step 7). Migration (step 8) confirmation is a flagged manual step, not automated (see script docstring). ✅ script done — **not executed against a live stack** in this sandbox (no network/Docker here); run it for real before considering step 14 actually confirmed.

**Backend enforcement and frontend auth support are both now live and wired end-to-end** (steps 1–12): a real user can sign up, log in, have their session survive a reload, get automatically logged out on an expired/revoked token, and have every project/log call correctly scoped to them. The only functional gap left in the auth plan itself is step 13 (rate limiting isn't enforced yet, just configured). Separately, the flywheel-scripts-vs-auth gap above needs resolving before the data flywheel can run against an authenticated deployment.

## Verified vs. not

Real build123d/npm/GPU were never available in this sandbox. Everything Python-side that doesn't need them was actually run and tested here (schema/compiler logic, `store.py`'s SQL including undo/redo edge cases and all auth-plan pieces above, the flywheel scripts' pairing/dedup/gate logic, `featureEdit.js`, `verify_auth_e2e.py`'s own syntax). All Python files pass `py_compile`; `verify_auth_e2e.py`'s CLI (`--help`) was smoke-tested but its actual HTTP checks were not run against a live service. All auth-related frontend JS/JSX (`App.jsx`, `api.js`, `LoginPage.jsx`, `SignupPage.jsx`, `ProjectBar.jsx`, `styles.css`) was verified via `esbuild` (real JSX parsing, full bundle-resolution confirming every local import — `./api`, `./components/*`, `./styles.css` — actually resolves) plus an explicit bracket-balance check (`{}`/`()`/`[]`) on every delivered file each turn. Anything touching real build123d execution, llama.cpp, a browser, or a live HTTP round-trip was verified against `stub_build123d/` (docstring-flagged as not a geometry check) or not at all — each README/script says explicitly which. Two real bugs were caught and fixed from actual user-reported tracebacks: a torch/torchvision ABI mismatch (pinned exact versions) and a tokenizer reconversion failure in `merge_adapter.py` (load tokenizer from `--base-model`, not `--adapter-dir`).

## Key decisions worth not re-litigating

- Direct interpreter, not IR→code generation
- SQLite, not Postgres (single-writer-per-project workload; swap point is `ProjectStore`'s method surface)
- Opaque session tokens, not JWT (need DB-backed revocation anyway) — this also means no signing secret to manage; `SESSION_LIFETIME_HOURS` is a pure UX/policy knob, not a security backstop, since logout revokes immediately regardless
- Session token persisted in plain `localStorage`, not a cookie or in-memory-only — same trust model `PROJECT_KEY` already established (it's an opaque, server-revocable token, not a long-lived secret; sensitivity is bounded by the session it represents)
- Legacy pre-auth rows (`owner_id`/`user_id IS NULL`) stay visible to any authenticated user as a deliberate stopgap until `migrate_legacy_owner.py` is run — not a bug, but don't ship to real users without running it (or explicitly deciding "legacy = permanently shared" and documenting that instead)
- `trl`'s `DataCollatorForCompletionOnlyLM` was removed upstream — dataset shape is `{prompt, completion}` + `SFTConfig(completion_only_loss=True)`, not the old collator approach
- Bounds-checking (`schema.validate_bounds`) lives in both the service layer (fast-path optimization) and `compiler.py` itself (actual guarantee) — deliberate, not redundant
- `localStorage` in the frontend is fine generally — it's a real standalone app, not a Claude Artifact, so that restriction doesn't apply
