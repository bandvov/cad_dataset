# Session Handoff — AI-Assisted CAD Service

Full project: JSON-IR CAD feature trees, compiled to real geometry via
build123d, generated by a fine-tuned Gemma 4, served through a multi-
service app with a three.js frontend. This file plus the project zip is
everything needed to continue in a fresh conversation.

## What's built (component map)

**Dataset/compiler core** (`cad_dataset/` root):
- `schema.py` / `compiler.py` — canonical JSON IR spec + direct interpreter (no codegen step) into build123d
- `executor.py` — subprocess isolation; `execute_ir()` one-shot, `BatchExecutor` persistent-worker pool (avoids per-call OCP import cost)
- `validator.py` — geometric sanity checks (manifold, volume>0, etc.)
- `gen_single_feature.py` / `gen_chains.py` / `gen_repair.py` / `gen_regenerate.py` — synthetic data generators for the 4 task types
- `build_dataset.py` — orchestrates generation → verify → dedupe (`structure_hash`) → split → chat-format (`to_chat_format`, `prompt`/`completion` shape); `--include-flywheel-data` flag merges verified flywheel records in
- `chat_format.py` — shared turn-rendering (`render_generate_user_turn` etc.), used by both `build_dataset.py` (training) and `llm-service/orchestrator.py` (inference) so wording can't drift between train/serve
- `primitives.py` — parameter samplers, safe ranges
- `stub_build123d/` — fake build123d for plumbing tests when a real install isn't available

**training/** — QLoRA fine-tuning (transformers/trl/peft), Docker + compose (`train`/`merge` services). `GeometryEvalCallback` reuses `schema.py`/`executor.py` for real geometry-validity eval during training. Explicit VRAM+RAM unload around eval's `generate()` calls (allocator fragmentation from interleaving backprop and KV-cache growth). `RESUME_FROM_CHECKPOINT` support.

**service/** — geometry microservice (FastAPI). `POST /v1/compile` (validate only), `POST /v1/export` (STEP/STL/GLB). `schema.validate_bounds()` rejects absurd IR (huge pattern counts, huge dimensions) before touching a worker — both here and inside `compiler.py` itself as the actual last line of defense.

**llm-service/** — inference orchestrator + product backend.
- `orchestrator.py` — self-correcting generate/repair loop against llama.cpp + geometry service; `generate_stream()` is the core implementation, `generate()` wraps it for non-streaming callers
- `store.py` — SQLite: projects+versions (undo/redo), request log (`log_event`/`compute_outcomes`, scoped by `user_id` — auth step 7), users/sessions, `verify_session()`'s lazy session-expiry (auth step 9), legacy-data backfill helpers (`count_legacy_rows`/`backfill_legacy_ownership`, auth step 8), **new**: `is_admin` column on `users` (+ migration guard) and `set_admin()` (flywheel-auth fix step 1)
- `rate_limiter.py` — `RateLimiter`, an in-memory fixed-window per-`user_id` request counter (auth step 13)
- `migrate_legacy_owner.py` — one-time CLI backfill driving `backfill_legacy_ownership`; dry-run by default, idempotent (auth step 8)
- `make_admin.py` — **new**: CLI to grant/revoke `is_admin` on an existing user, same dry-run-by-default/`--apply` shape as `migrate_legacy_owner.py` (flywheel-auth fix step 4). Does NOT create accounts — target user must already exist.
- `main.py` — FastAPI: `/v1/auth/{signup,login,logout}`, `/v1/generate(/stream)`, `/v1/projects/*` (CRUD, generate, apply, undo, redo, render, log-download — all behind `Depends(get_current_user)`), `/v1/logs*` (scoped by `user_id`); `rate_limit_middleware()`, ASGI middleware enforcing `RATE_LIMIT_PER_MINUTE` per authenticated `user_id` (auth step 13); **new**: `get_current_admin_user()` dependency (403 if `not user.is_admin`) and `/v1/admin/logs`, `/v1/admin/logs/outcomes`, `/v1/admin/logs/summary` — unscoped (cross-user) versions of the `/v1/logs*` routes, for the flywheel miners (flywheel-auth fix steps 2-3)
- docker-compose: `llamacpp` (ghcr.io/ggml-org/llama.cpp) + this service + `convert` profile (HF→GGUF); `SESSION_LIFETIME_HOURS`/`RATE_LIMIT_PER_MINUTE` env passthrough (auth step 9, now actually enforced by step 13)

**frontend/** — three-panel React app (feature tree / three.js viewport / chat), titlebar project switcher. Design: charcoal + steel-cyan accent, IBM Plex Mono for technical data, drafting-table register (see `frontend/README.md` for full rationale). Structured editing (click a feature, edit a field, bypasses the model). Download toolbar (STEP/STL/GLB) in the viewport. Inline project rename (pencil icon, titlebar dropdown).
- `components/LoginPage.jsx` / `components/SignupPage.jsx` — auth step 10
- `App.jsx` — gates rendering behind `authToken` state; `applyAuth()`/`clearSessionState()` keep React state, `api.js`'s in-memory token, and `localStorage["cad_auth"]` in sync; restores a persisted session on mount before the project-list effect fires (auth steps 10–11); registers a global 401 handler that drops back to login with a "session expired" notice (auth step 12)
- `api.js` — `login()`/`signup()`/`logout()`; every `/v1/projects*` call goes through `authFetch()`, which attaches `Authorization: Bearer <token>` and routes any `401` through a registered handler (auth steps 11–12). **Not yet updated for step 13**: a 429 from the new rate-limit middleware is NOT specially handled here — it'll surface as a generic `Error` via `handleResponse()`'s `!res.ok` branch (same path as any other non-2xx), which is functionally fine (the error reaches the chat log / rename-error message) but doesn't show a "slow down" message or honor `Retry-After` with a backoff/retry. Worth a small frontend follow-up if 429s become common in practice.
- `components/ProjectBar.jsx` — shows the logged-in email + a Log out button + inline rename

**Root `docker-compose.yml`** — runs the whole app (`geometry`+`llamacpp`+`llm-service`+`frontend`) as one stack, one `.env`. Deliberately excludes `training/` and `convert` (offline steps).

**`verify_auth_e2e.py`** (repo root) — auth plan step 14: HTTP-driven end-to-end check against a running stack (signup→login→create project; a second user gets 404 on GET/DELETE of the first user's project and it's absent from their list; request-log scoping). Exit 0/1, same convention as `mine_flywheel_gate.py`. Migration (step 8) verification is a flagged **manual** step (`--expect-migrated` prints the `migrate_legacy_owner.py` dry-run command) — no HTTP endpoint exposes legacy row counts by design. **Not run against a live stack in this sandbox** (no network/Docker here) — run it before treating step 14 as confirmed. Does not yet exercise step 13 (rate limiting) — would need a small addition (hammer an endpoint N+1 times, expect a 429) if you want that covered by the same script rather than just the ad-hoc TestClient check done during step 13's implementation.

**✅ Flywheel-scripts-vs-auth gap — RESOLVED this session** (was the auth-step-7 gap flagged previously). Five-step fix, all done and verified for real against a live server (see below):
1. `store.py`: `is_admin` column on `users` + `set_admin()`.
2. `main.py`: `get_current_admin_user()` dependency (403, not 404 — the caller IS authenticated, just lacks privilege).
3. `main.py`: `/v1/admin/logs`, `/v1/admin/logs/outcomes`, `/v1/admin/logs/summary` — same shapes as `/v1/logs*` but unscoped (`user_id=None`), behind the admin dependency. Separate routes, not a flag on the existing ones, so the cross-user bypass never touches normal user-facing code paths.
4. `make_admin.py`: CLI to grant/revoke admin on an existing user.
5. `flywheel_common.py` / `mine_flywheel_data.py` / `mine_flywheel_pairs.py` / `mine_flywheel_repairs.py` / `mine_flywheel_edits.py`: all now require `--auth-token` (an admin session token; also readable from `LLM_SERVICE_ADMIN_TOKEN`), send it as `Authorization: Bearer <token>`, and the two log-fetching scripts hit `/v1/admin/logs*` instead of the user-scoped routes.

**Known remaining limitation, by design, not a bug**: version-fetch (`GET /v1/projects/{id}/versions/{index}`, used to resolve a fix's `json_ir`) is **owner-scoped** and does **not** treat `is_admin` as a bypass — an admin token only resolves fix versions for projects it happens to own. Confirmed directly: the same admin token 404's against another user's project and succeeds once granted to that project's actual owner. Callers already degrade this to "skip, count as unresolved" rather than crashing (unchanged behavior), so this reduces flywheel coverage of other users' fixes rather than breaking anything. Real fix would be an admin-scoped version route or an ownership bypass for admins on that route — worth doing if cross-user fix coverage matters in practice; out of scope for this pass, which was specifically about the log-visibility gap.

**Verified for real, not just syntax-checked**: ran an actual `uvicorn` instance of `main.py` against a live SQLite DB, seeded two ordinary users + one admin via real HTTP signup, granted admin via the real `make_admin.py` CLI, seeded a real failure→fix event chain via `store.py`, then ran `mine_flywheel_data.py` → `mine_flywheel_pairs.py` as real subprocesses over real HTTP. Confirmed: a non-admin token gets a clean 403; an admin token sees both users' events in one fetch; the full pipeline produces a correct broken/fixed IR pair end-to-end; and the version-fetch ownership limitation above reproduces exactly as documented, then resolves correctly once the token is granted to the actual project owner.

## Auth (14 of 14 plan steps implemented — only live verification remains)

Full plan, all 14 steps, current status:

1. **Schema** — `users` table (id, email, password_hash, created_at), nullable `owner_id` on `projects`, migration guard (`ALTER TABLE` for pre-existing DB files). ✅ done
2. **Password handling** — `hash_password`/`verify_password`, stdlib PBKDF2-HMAC-SHA256, no bcrypt/argon2 dependency. ✅ done
3. **Token issuance** — opaque session tokens over JWT (need DB-backed revocation anyway). `sessions` table + `create_session`/`verify_session`/`delete_session`. ✅ done

5. **Auth dependency** — `get_current_user` (FastAPI `Depends`): reads `Authorization: Bearer <token>`, `verify_session` → `store.get_user`, 401 on either failure. `POST /v1/auth/logout` behind the same dependency. ✅ done
6. **Scope project endpoints** — `Depends(get_current_user)` on all `/v1/projects*` routes (including the newer `PATCH` rename route). `_require_owned_project(project_id, user)`: 404 (not 403) on missing-or-not-owned. `create_project`/`list_projects` scoped by `owner_id`. Legacy rows (`owner_id=NULL`) stay accessible to any authenticated user until step 8's backfill runs. ✅ done
7. **Scope the request log** — `user_id` column on `request_log` (+ migration guard), threaded through every `log_event` call; `list_events`/`log_summary`/`compute_outcomes` scoped by `user_id`, with legacy `user_id IS NULL` rows staying visible (same stopgap as step 6). `/v1/logs*` gated behind `Depends(get_current_user)`. ✅ done. The flywheel-scripts-vs-auth gap this step originally left open (regular user tokens can't see cross-user log data, and the scripts weren't even sending one) is **resolved** — see the flywheel-auth fix above (`is_admin`, `get_current_admin_user`, `/v1/admin/logs*`).
8. **Migration for existing data** — `store.count_legacy_rows()`/`backfill_legacy_ownership()`; `migrate_legacy_owner.py` CLI (dry-run by default, `--apply` to write, idempotent — only NULL columns ever touched). Stateless `/v1/generate` events (no `project_id`) are intentionally left unmigrated forever, not a bug. ✅ done
9. **Secrets/config** — no signing secret needed for opaque tokens. `SESSION_LIFETIME_HOURS` wired into `ProjectStore.verify_session()`'s lazy expiry-and-delete-on-read (blank/unset = never expires; revocation via logout is immediate regardless). `RATE_LIMIT_PER_MINUTE` added to `.env.example`/compose files as a config knob — now actually read by step 13's middleware, not just inert. ✅ done
10. **Frontend: login/signup UI** — `LoginPage.jsx`/`SignupPage.jsx`; `App.jsx` gates all rendering behind `authToken` state (`authView` toggles between the two). ✅ done
11. **Frontend: token storage** — `api.js`'s `setAuthToken()`/`authHeaders()` attach `Authorization: Bearer <token>` to every `/v1/projects*` call and `logout()`. `App.jsx`'s `applyAuth()` persists `{token, user}` as one JSON blob in `localStorage["cad_auth"]` and restores it on mount, before the project-list effect can fire. ✅ done
12. **Frontend: 401 handling** — `api.js`'s `authFetch()` is the single choke point that detects a 401 and invokes a handler `App.jsx` registers via `setUnauthorizedHandler()`. `clearSessionState()` (shared by explicit logout and the forced case) clears token, user, stored project id, and all in-memory project state together. A forced logout sets `sessionExpired`, shown as a notice on `LoginPage`. ✅ done
13. **Rate limiting (keyed on user_id)** — **✅ done this session.** `llm-service/app/rate_limiter.py`'s `RateLimiter`: in-memory, fixed-window (per wall-clock minute) counter keyed on `user_id`, guarded by a `threading.Lock` (same pattern as `store.py`'s cursor lock). Wired in as `main.py`'s `rate_limit_middleware()` — ASGI middleware (not a per-route dependency), so it covers every current and future route uniformly. It re-verifies the session token via the same `STORE.verify_session()` call `get_current_user()` already makes (no second auth mechanism introduced); requests with no valid session token pass through untouched (signup/login/health, and the stateless `/v1/generate` path, none of which have a `user_id` to key on). Reads `RATE_LIMIT_PER_MINUTE` from the environment (default 60, the value already shipped in `.env.example` since step 9); `<= 0` disables limiting entirely. On block, returns `429` with `{"detail": "rate limit exceeded (<N> requests/minute)"}` and a `Retry-After` header (seconds to the next window). **Verified for real** (unusually for this project — see below): actually installed `fastapi`/`httpx` in the sandbox and ran both a standalone unit test of `RateLimiter` (window rollover, per-user isolation, the `<=0` off-switch, `reset()`) and a full `TestClient` integration test through the real `main.py` app (signup → login → 5 allowed requests → 3× `429` with `Retry-After` present → a second user's budget confirmed independent → unauthenticated `/v1/generate` confirmed unaffected). All assertions passed. **Known limitation, by design**: in-memory only — resets on container restart, not shared across replicas if `llm-service` is ever horizontally scaled (see `rate_limiter.py`'s docstring for what to swap in — Redis INCR+EXPIRE — if that happens). **Frontend gap**: `api.js` doesn't special-case a `429` yet (see `frontend/` notes above) — functional but not polished.

## Key decisions worth not re-litigating

- Direct interpreter, not IR→code generation
- SQLite, not Postgres (single-writer-per-project workload; swap point is `ProjectStore`'s method surface)
- Opaque session tokens, not JWT (need DB-backed revocation anyway) — this also means no signing secret to manage; `SESSION_LIFETIME_HOURS` is a pure UX/policy knob, not a security backstop, since logout revokes immediately regardless
- Session token persisted in plain `localStorage`, not a cookie or in-memory-only — same trust model `PROJECT_KEY` already established (it's an opaque, server-revocable token, not a long-lived secret; sensitivity is bounded by the session it represents)
- Legacy pre-auth rows (`owner_id`/`user_id IS NULL`) stay visible to any authenticated user as a deliberate stopgap until `migrate_legacy_owner.py` is run — not a bug, but don't ship to real users without running it (or explicitly deciding "legacy = permanently shared" and documenting that instead)
- Rate limiting is **in-memory, fixed-window, single-instance-only by design** (auth step 13) — a deliberate choice to avoid adding Redis or similar to a project this size; revisit only if `llm-service` is ever run as more than one replica
- Admin is a per-user boolean flag (`is_admin`), not a separate service-account/API-key mechanism — reuses the existing revocable session-token model rather than adding a second credential type to manage
- Admin bypasses ownership scoping on the **log routes** (`/v1/admin/logs*`) but deliberately NOT on **project/version routes** (`_require_owned_project()`) — those weren't in scope for the flywheel-auth fix and remain owner-only; see the flywheel pipeline section's "known remaining limitation" note
- `trl`'s `DataCollatorForCompletionOnlyLM` was removed upstream — dataset shape is `{prompt, completion}` + `SFTConfig(completion_only_loss=True)`, not the old collator approach
- Bounds-checking (`schema.validate_bounds`) lives in both the service layer (fast-path optimization) and `compiler.py` itself (actual guarantee) — deliberate, not redundant
- `localStorage` in the frontend is fine generally — it's a real standalone app, not a Claude Artifact, so that restriction doesn't apply
